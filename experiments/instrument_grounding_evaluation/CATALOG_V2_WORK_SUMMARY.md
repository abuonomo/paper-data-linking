## 1. Problem

GitLab issues (NASA GitLab, `hdrl/paper-data-linking`) traced grounding/validation
false negatives to catalog descriptions:

- **#171**: `spase://SMWG/Instrument/Ulysses/FGM` described as FGM-only; record is
  actually the combined HED/VHM/FGM magnetic-field investigation → "vector helium
  magnetometer" mentions rejected.
- **#172**: paper says "PM on board SOHO"; CELIAS description doesn't enumerate
  sub-detectors (CTOF/MTOF/PM/STOF/SEM) → validator can't confirm parent-child.
- **#156**: same class — suite descriptions lack detector enumeration generally.
- **#173**: Wind *mission* description says only "halo orbit at L1"; Wind spent
  1994-2004 in elliptical magnetospheric orbits → 1998 radiation-belt observations
  rejected ("presentism").
- NOT description-fixable: #169 (reversed tstzrange aborts DatasetUsage inserts —
  code bug in `api/vso_query_builder/tasks.py`), #170 (mission-list index
  off-by-one — prompt format), #152 (combined MDI→HMI time spans — the time
  normalizer prompt is only `Parse this time range: "{{ raw_time }}"`, it never
  sees catalog context).

Root cause (audited): descriptions are LLM summaries capped at 200 chars with an
explicit "Do NOT include operational dates" rule, generated by
`enrich_catalog_from_spase.py` (keeps only first sentence of SPASE description,
discards ResourceName) + `enrich_catalog_with_llm.py` (v1). Schema is a single
`description` TextField on `Observatory`/`Instrument`
(`api/vso_query_builder/models.py`); descriptions feed pgvector embeddings
(auto-regenerated on save) and three prompts: mission-identification list,
`prompts/validation/user.xml`, `prompts/mission_validation/user.xml`.
Decision: fix via richer free-text descriptions, NOT schema changes.

## 4. Critical lesson: description framing determines validator verdicts

Replay-tested with the exact prod validation prompts and model
(`bedrock/converse/openai.gpt-oss-120b-1:0`, temp 1.0 — the model behind the
original failures; gpt-5.4 passes everything regardless, only gpt-oss-120b is
description-sensitive). Harness:
`scratches/replay_validation_failures.py` (env `REPLAY_MODEL` to switch models;
parses `FINAL DECISION: **valid|invalid**` — note the `\**` in the regex).

- **#173 Wind**: old mission desc → invalid 3/3; orbital-history desc → valid 3/3. FIXED.
- **#172 PM→CELIAS**: not reproducible (9/9 valid even with old desc); v2 desc is insurance.
- **#171 Ulysses**: gpt-5.5's first v2 desc made it WORSE (0/3): it framed the
  record as "FGM ... one of the two sensors alongside VHM" → validator applied
  the sibling-match-INVALID rule. Framing the record as "magnetic field
  investigation (HED/VHM/FGM), combining FGM and VHM" → valid 5/5.

**Rule derived**: the validator treats the description as the definition of the
record's SCOPE. Records whose SPASE ID names one sensor but whose ResourceName/
description show combined scope MUST be described as the combined investigation
("combining/comprising"), never as "one sensor alongside its sibling". A CAUTION
rule encoding this is now in the v2 script's system prompt (verified 3/3 compliant
on resample; pre-patch prompt was 3/3 sensor-framing). Root cause of the bad
framing: the catalog's own `instrument_name` field for that record is the literal
string "FGM" (URI-derived), which told the model the entity was the sensor.

Catalog-wide sweep for other instances: only the 4 Ulysses entries have the
multi-part-parenthetical pattern; FGM was the only bad framing (patched). A
"consists of multiple sensors but no combining-language" scan returned 0 hits.
"Alongside X where X has no own record" flags (~52) are mostly benign (sibling
genuinely has separate data → rejection is correct) but expose **coverage gaps**:
no catalog record for Ulysses COSPIN, Wind SMS/MASS, DSCOVR MAG (CDAWeb
DSCOVR_H0_MAG exists!), DMSP SSIES/SSUSI/SSULI, Polar CAMMICE/HIT, C/NOFS
CINDI/NWM, EUNIS LW channels. Memory file:
`project_description_framing_validation.md` in the agent memory dir.

## 8. Operational gotchas (will bite you)

- `litellm.acompletion` has NO default timeout — runs hung 50 min with zero open
  sockets. Always pass `timeout=180, num_retries=2`. Even WITH those params,
  inline litellm Bedrock calls hung repeatedly (zero sockets, zero CPU) in this
  environment; direct `boto3 bedrock-runtime converse` with
  `Config(connect_timeout=10, read_timeout=120)` worked instantly every time.
  Prefer boto3 for ad-hoc Bedrock replay calls.
- litellm leaves async clients open; scripts linger after `main()` returns
  (background-task completion notifications fire late). Judge completion by
  output files, not process exit.
- Python buffers stdout when backgrounded — launch with `PYTHONUNBUFFERED=1`.
- AWS for Bedrock replay: static keys in `.env` rot; refresh via
  `aws sso login --profile bedrock` + `./scripts/refresh-aws-credentials.sh`.
- zsh eats `===` in heredoc-adjacent echo args; `cd` in compound commands can
  reset between calls — use absolute paths.
- `dotenv.find_dotenv()` raises AssertionError under `python - <<EOF`; use
  `load_dotenv(".env")` with explicit path.
